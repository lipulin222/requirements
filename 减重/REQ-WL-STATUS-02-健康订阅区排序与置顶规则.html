REQ-WL-STATUS-02 · 健康订阅区排序与置顶规则

需求单 · 科学减重（WL） · 交付目标：可上线面向用户使用（H5 + 微信小程序）

编号 REQ-WL-STATUS-02 ｜ 项目：科学减重（WL）｜ 模块：服务状态与卡片 ｜ 优先级 P0 ｜ 状态：待评审 相关 Demo：线上服务页 埋点：见 REQ-WL-BASE-01 数据上报规范 ｜ 上线基线：见 REQ-WL-BASE-02

1. 背景与目标

问题：健康订阅区（原专项健康管理）里有减重、过敏、痤疮、心理等多张专项卡，目前顺序写死——减重卡即使在服务中也可能排在后面，未上线的专项也会占位。

目标：明确多张卡之间的排序规则——判定成立的减重卡置顶，其余卡按服务端下发顺序排，未上线专项不渲染，无服务中卡片时走默认顺序并给引导。

本单只管卡与卡之间的顺序；「是否服务中」由 STATUS-01 判定，「单张卡内部渲染」由 STATUS-03 定义。

2. 规则

2.1 排序优先级

层级 规则
1 STATUS-01 判定成立（进行中 / 维持期）的减重卡 → 置顶
2 其余专项卡按服务端下发的 order 升序
3 order 相同 → 按最近活跃时间倒序
4 未上线 / 未配置的专项不渲染，不占位置
  • 同一时间最多一张置顶卡。
  • 若多张专项同时处于服务中：取「最近一次服务开始时间最晚」的置顶，其余按序排后。

2.2 置顶的影响面

  • 只改顺序：不改卡片结构，不影响其他卡可见性。
  • 其他专项卡仍然可见（滚动可及），不折叠、不隐藏。
  • 置顶必须在首屏渲染前确定（服务端预判定或骨架屏），禁止卡片位置跳动。

2.3 默认顺序与空态

  • 判定数据不可用（接口超时/失败）→ 按服务端默认顺序渲染，不置顶，并上报 service_detect_fail。
  • 无任何专项卡片 → 展示新客引导，不留白块。

2.4 配置化

  • 专项列表、是否上线、order 全部由服务端配置下发，前端不写死。
  • 卡片数量上限与折叠策略由服务端配置控制。

3. 字段与接口

接口

GET /health/subscriptions

项 内容
请求参数 user_id、platform（h5 / wxapp）
响应 cards[]、pinned_card、default_order[]
异常码 401/403 未授权 → 跳登录；500 → 降级默认顺序；timeout → 降级默认顺序
降级 接口失败一律按 default_order 渲染且不置顶，不阻塞页面

字段

cards[] 单项：

字段 说明
type 专项类型（weight / allergy / …）
in_service 是否服务中（来自 STATUS-01 判定）
stage 未开始 / 进行中 / 维持期 / 已结束
pinned 是否置顶（服务端算好的最终结果，前端直接用）
order 排序权重
title / status_text 卡标题 / 状态文案
cta 主行动（由 STATUS-03 定义内容）

pinned_card：置顶卡类型，无则 null。

4. 验收与上线要求

验收清单

  • 判定成立的减重卡排在第一位
  • 其他专项卡仍可见，只是排序在后，未被隐藏
  • 未上线专项不渲染
  • 接口失败时按默认顺序渲染且不置顶，页面其余部分正常
  • 无任何卡片时展示引导，无白块
  • 专项列表与 order 来自服务端配置，前端无硬编码顺序
  • 限速 Slow 3G 下打开页面，卡片从出现到稳定无位移
  • 多张卡同时服务中时，取「最近开始」的置顶

上线要求（本单特有）

  1. 排序结果由服务端计算并下发 pinned，前端不自行判断优先级。
  2. 订阅区数据与首屏数据合并下发，避免二次请求导致跳动。
  3. 小程序与 H5 两端顺序一致。

5. 依赖与风险

项 说明 应对
依赖 STATUS-01 置顶前提是判定成立 本单只消费 in_service / pinned
依赖 STATUS-03 卡片内容由该单定义 本单只定顺序
配置错误导致排序混乱 服务端 order 配置错误会直接反映到首屏 配置需可观测，异常可快速回滚
未上线专项占位 早期版本会渲染未上线专项 服务端不下发即不渲染

6. 待决策

  1. 除减重外的其他专项（过敏/痤疮/心理）本期是否上线？不上线则订阅区只有减重卡，是否还需要排序规则？
  2. 置顶卡数量上限是否固定为 1 张？未来若多个专项都要置顶怎么处理？
  3. 卡片数量超过几张时是否折叠？折叠规则由运营配置还是产品定死？
  4. 「最近活跃时间」的定义（最后点击时间 / 最后服务时间 / 创建时间）以哪个为准？
