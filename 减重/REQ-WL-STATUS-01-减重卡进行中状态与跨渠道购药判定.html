REQ-WL-STATUS-01 · 减重卡「进行中」状态：跨渠道处方与购药判定

需求单 · 科学减重（WL） · 交付目标：可上线面向用户使用（H5 + 微信小程序）

编号 REQ-WL-STATUS-01 ｜ 项目：科学减重（WL）｜ 模块：服务状态与卡片 ｜ 优先级 P0 ｜ 状态：待评审 相关 Demo：线上服务页 ｜ 确认购药页 ｜ AI 减重助理 埋点：见 REQ-WL-BASE-01 数据上报规范

1. 背景与目标

问题：已在线下开药、或经客服下单、正在用药的用户，进线上服务页时减重卡仍显示「未开始」，线上不认线下的服务状态。

目标：只要用户同时有「医生处方」+「支付购药记录」（不论哪个渠道），进线上服务页时：① 健康订阅区置顶减重卡；② 卡片直接是**「进行中」**，按真实疗程进度展示。

2. 规则

2.1 数据来源（三渠道归一为一条服务记录）

渠道 处方 支付 负责系统
A 线上自助 线上处方 订单中心 本系统
B 客服协助 线上处方（客服代发起） 订单中心 客服系统 + 本系统
C 线下门诊 HIS 处方 门诊收费 门诊 HIS
  • 三渠道归一为 service_record（字段见第 3 节），前端只消费判定结果，不做渠道判断。
  • 渠道不参与优先级：任一渠道成立即成立，不存在"线上优先于线下"。
  • 多条并存：按仍在服务期内、起始时间最晚的那条算进度（按时间排序，不按渠道）。

2.2 判定

结论 条件
成立 有有效处方（未作废/未过期）且有对应支付成功记录，且两者可关联（同次就诊/同笔订单）
不成立 任一条件不满足；或线下记录未匹配到用户（见 2.5）
回退 处方作废、支付退款、疗程结束超期、用户主动终止 → 撤回置顶与「进行中」
  • 服务起始时间 = pay_time（支付成功时间），不是处方开具时间，也不是下单时间。
  • 渠道来源不对用户展示（UI 不出现"线上/客服/线下"），仅用于埋点与问题定位。

2.3 服务期与进度（按剂量，不按固定周数）

服务期由本次购药剂量规格推算：

阶段 剂量
第 1 个月 2.5 mg / 周
第 2 个月 5 mg / 周
第 3 个月 7.5 mg / 周
…… 依此类推
封顶 15 mg
  • 进度（第几个月 / 当前剂量）由 pay_time + 剂量爬坡推算。
  • 本次购药剂量可覆盖的周期结束且无新购药 → 服务期结束。
  • 续费/再次支付：接着算，不重置，不回到「未开始」。

2.4 状态流转与展示

状态 置顶 说明
未开始 否 无有效处方或支付
进行中 是 判定成立；状态标签 teal，不得显示「未开始」
维持期 是（2 个月） 服务期结束后转维持期，继续置顶 2 个月
已结束 否 维持期满 2 个月后转结束，不再置顶
  • 置顶只改顺序：其他专项卡仍可见，只是排在减重卡之后。
  • 置顶必须在首屏渲染前定完（服务端预判定或骨架屏），禁止卡片位置跳动。
  • 判定数据不可用（超时/缺字段）→ 降级为不置顶，不展示错误状态，也不阻塞页面其他部分。
  • 有数据才展示：体重变化等模块无数据则隐藏，不得编造、不留白块。
  • 产品 UI 不出现阶段编号、进度条等内部信息。

2.5 线下用户匹配

  • 以 user_id（unionid/会员号）为主键。
  • 线下无账号时按 手机号 + 姓名 匹配；不用身份证。
  • 双因子必须同时一致才关联；匹配失败即不展示（合规：串号=他人医疗数据被看到）。
  • 匹配结果留痕可追溯。

3. 字段

service_record（归一后，服务端产出）：

字段 说明
user_id 用户唯一标识
channel online / cs / clinic
prescription_id / prescription_status 处方号 / 有效·已作废
pay_id / pay_status / pay_time 支付流水 / 成功·已退款 / 服务起始时间
sku / plan_id 药品 / 方案
dose_mg / month_index 当前剂量（mg/周）/ 处于第几个月
doctor_id / clinic_id 开方医生 / 机构（线下必填）

判定输出（前端消费）：

{ in_service, stage, plan_id, start_date, month_index, dose_mg, source_channel }
  • stage：未开始 / 进行中 / 维持期 / 已结束
  • month_index：按剂量爬坡推算的月序

4. 验收与上线要求

验收清单

  • 三渠道各自「有效处方 + 支付成功」后，线上均能看到置顶减重卡
  • 置顶后状态为「进行中」，代码中不存在回落「未开始」的路径
  • 进度按剂量爬坡推算（2.5 → 5 → 7.5… → 15 封顶），续费接着算不重置
  • 服务期结束后转维持期、继续置顶 2 个月，之后转结束不再置顶
  • 退款 / 处方作废可撤回置顶与状态
  • 多渠道并存：渠道不参与优先级，按「服务期内起始最晚」算进度
  • UI 不出现渠道来源
  • 线下手机号 + 姓名不匹配时不展示，无技术口径暴露
  • 判定失败降级不置顶，页面其他部分正常
  • 首屏无卡片位置跳动
  • 客服渠道订单均带 user_id，无无主订单

上线要求（本单特有；通用基线见 REQ-WL-BASE-02）

  1. 判定与首屏数据合并下发（或前置请求）；客服/线下 T+1 同步可接受，并提供人工同步入口。
  2. 判定结果需服务端可观测、可人工修正（判定错误直接影响首屏主卡）。
  3. 匹配留痕 + 双因子校验，满足健康数据合规要求。
  4. 小程序与 H5 两端呈现一致。

5. 依赖与风险

项 说明 应对
门诊 HIS 打通 最大外部依赖：需给处方号、支付流水、医生、时间并关联用户 本单只定字段契约，需门诊配合
用户匹配串号 匹配错误 = 他人医疗数据被看到（严重合规风险） 双因子 + 失败即不展示 + 留痕
数据延迟 客服/线下 T+1，状态滞后一天 已确认可接受；补人工同步入口
客服无主订单 未回写 user_id 导致判定失败 客服系统强制回写 + 流程校验
依赖卡片渲染与容器单 卡片渲染与容器排序由对应单承载 本单只给判定与置顶规则

6. 待决策

  1. 剂量爬坡超过 15 mg 封顶后的维持用量与周期如何计算？（影响维持期 2 个月的起算点）
  2. 服务期结束判定：以「本次购药剂量用完」为准，还是以「距上次支付超过 N 天」兜底？两者都要还是其一？
  3. 维持期的 2 个月是否需要可配置（运营侧调整）？
  4. 线下同一用户存在多条未结束记录时，是否允许合并计算总进度，还是严格取最晚一条？
